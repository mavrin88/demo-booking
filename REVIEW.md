# Ревью API бронирования

Разобран исходный `BookingController` до исправления `store` и `destroy`. Методы `index` и `today` по условию не менялись: ниже описано, что в них сломано и как это чинить, но в коде они оставлены как были.

## Critical

### 1. SQL-инъекция в `store`

Конфликт ищется запросом, в который подставляются поля запроса. Проверки типов до запроса нет.

```php
$conflict = DB::select("SELECT id FROM bookings
    WHERE room_id = {$request->room_id}
    AND starts_at <= '{$request->ends_at}'
    AND ends_at >= '{$request->starts_at}'");
```

`room_id` попадает в SQL без кавычек, даты — внутрь строковых литералов. Значение `1 OR true` снимает фильтр комнаты, кавычка в `starts_at` / `ends_at` обрывает литерал. Запрос выполняется первым делом, поэтому невалидное тело сразу бьёт в базу и вместо 422 даёт 500.

Как исправить: после валидации строить запрос через query builder, чтобы значения ушли в привязки, а не в текст SQL.

### 2. Автор брони берётся из тела запроса

`Booking::create($request->all())` при `user_id` в `#[Fillable]` записывает того пользователя, которого прислал клиент. Токен на автора не влияет. Можно создать бронь от чужого имени: после правила «отменяет только автор» это ещё и способ повесить чужую бронь на другого человека или, наоборот, оставить себе чужой слот. Если `user_id` не передать, вставка падает с 500 из-за `NOT NULL`.

Как исправить: автор — только текущий пользователь. `user_id` убрать из fillable и выставлять через `associate`. Поле в JSON можно игнорировать, чтобы пример из README продолжал работать.

### 3. Отменить бронь может любой авторизованный пользователь

```php
Booking::findOrFail($id)->delete();
```

Владелец не сравнивается с пользователем токена. Чужую бронь можно удалить. Нечисловой `{id}` на PostgreSQL даёт 500 (`invalid input syntax for type bigint`), а не 404: строка уходит в сравнение с `bigint` как есть.

Как исправить: policy `delete`, отказ с 403, если пользователь не автор. В маршруте — неявная привязка модели и `whereNumber`, чтобы мусорный id был 404.

## Major

### 4. Стык двух встреч считается конфликтом

Условие `starts_at <= конец новой AND ends_at >= начало новой` включает границы. Брони 10:00–11:00 и 11:00–12:00 пересекаются в точке 11:00 и отклоняются. По правилам это не пересечение.

Как исправить: полуинтервал `[начало, конец)`: существующая бронь конфликтует, только если `starts_at < конец новой` и `ends_at > начало новой`.

Отдельно: ISO-строка сравнивается с колонкой `timestamp without time zone`. PostgreSQL приводит строку со смещением к `TimeZone` сессии и отбрасывает пояс. Eloquent пишет метки в UTC (`APP_TIMEZONE`). Если пояс сессии не UTC, проверка съезжает. Сравнивать нужно уже разобранные абсолютные метки.

### 5. Рабочие часы проверяются не у того офиса и не у всего интервала

```php
$start = Carbon::parse($request->starts_at);
if ($start->hour < 9 || $start->hour >= 20) {
    return response()->json(['error' => 'Нерабочее время'], 422);
}
```

Час берётся в смещении клиента, а не в `offices.timezone` комнаты.

- `09:00+07` для комнаты в Москве — это 05:00 по Москве, проверка пропускает.
- `19:00+03` для комнаты в Новосибирске — это 23:00 по Новосибирску, проверка тоже пропускает.
- Конец не смотрится: 10:00–23:00 проходит, если час начала попал в диапазон.
- Минуты не учитываются.
- Нет проверки, что обе метки лежат в одном местном дне. Окно 09:00–20:00 — это окно конкретного дня офиса.

Как исправить: разобрать ISO 8601 в абсолютное время, перевести начало и конец в пояс офиса и убедиться, что это один местный день, начало не раньше 09:00, конец не позже 20:00.

### 6. Нет длительности и шага 15 минут

Принимается бронь на минуту, на сутки и на 10:07. Нужный диапазон — от 15 минут до 4 часов, начало и конец на сетке 15 минут по местному времени офиса (10:00, 10:15, 10:30, 10:45).

Как исправить: длительность в секундах и отдельно минуты и секунды обеих меток после перевода в пояс офиса.

### 7. Невалидный ввод отвечает 500 или чужим форматом, а не 422

Form request нет. Несуществующая комната, пустое тело, перевёрнутый интервал, недата — исключение Carbon или базы. Конфликт возвращает 409 и тело `{"error": "..."}`, обычная валидация Laravel — 422 и `errors`. Для правил бронирования нужен один понятный 422.

Как исправить: `StoreBookingRequest` и те же `ValidationException` для длительности, рабочих часов и занятого слота.

### 8. Два одновременных запроса создают две брони

Проверка и `INSERT` не в одной транзакции и без блокировки. Оба запроса не видят строку друг друга. Для последовательных вызовов хватает правильного условия, для гонки — нет.

Как исправить: транзакция и `SELECT ... FOR UPDATE` по строке комнаты. Блокировка самих броней через `exists()` не сериализует две вставки в пустой слот: блокировать нечего. Поверх этого — ограничение PostgreSQL `EXCLUDE USING gist` по `room_id` и `tsrange(starts_at, ends_at, '[)')`. Оно удерживает инвариант и для вставок мимо HTTP. Полуинтервал `[)` как раз разрешает стык. Нарушение `23P01` ловить и отдавать тем же 422, а не 500.

Колонки — `timestamp without time zone`, поэтому диапазон именно `tsrange`, не `tstzrange`. Для оператора `=` по `bigint` внутри GiST нужно расширение `btree_gist`.

### 9. `today` считает «сегодня» в UTC приложения

```php
return $room->bookings()
    ->whereDate('starts_at', today())
    ->get()
    ->map(fn ($b) => [
        'time' => $b->starts_at . ' – ' . $b->ends_at,
        'author' => $b->user->name,
    ]);
```

`today()` и `whereDate` живут в `APP_TIMEZONE` (UTC). У Москвы ошибка на границе суток, у Новосибирска (UTC+7) — семь часов: местная полночь уже другой календарный день. В ответ попадает конкатенация Carbon, это `Y-m-d H:i:s` в UTC, без пояса офиса. В `map` читается `$b->user` без `with('user')` — N+1. `whereDate` оборачивает колонку в функцию и не пользуется индексом по `starts_at`.

Как исправить, когда метод войдёт в скоуп: границы местных суток офиса перевести в UTC и фильтровать по ним, время в ответе форматировать в поясе офиса, пользователя жадно подгрузить.

## Minor

### 10. `booking_id` не попадает в `storage/logs/bookings.log`

```php
Log::withContext(['booking_id' => $booking->id]);
Log::channel('bookings')->info('Booking created');
```

У `LogManager` нет `withContext`. Вызов уходит в `__call` и применяется к каналу по умолчанию (`stack` → `single`, файл `laravel.log`). Канал `bookings` — другой логгер, его контекст пустой. В `bookings.log` остаётся строка `Booking created` без идентификатора. Сам факт создания в файл пишется, поэтому это не потеря журнала целиком, но код не делает того, что выглядит на первый взгляд.

Как исправить: передать контекст вторым аргументом именно канала `bookings`:

```php
Log::channel('bookings')->info('Booking created', [
    'booking_id' => $booking->id,
]);
```

Писать лог после коммита транзакции, чтобы в журнал не попадала бронь, которую база отвергла.

### 11. Запрос без `Accept` отвечает 500, а не 401

README описывает это как особенность API. В `bootstrap/app.php` для `api/*` уже включён `shouldRenderJsonWhen`, но он не успевает сработать.

`Authenticate` для гостя без `Accept: application/json` сразу строит редирект через `route('login')`. Маршрута `login` нет, поэтому летит `RouteNotFoundException` со статусом 500. До рендера `AuthenticationException` выполнение не доходит.

Как исправить: для `api/*` не строить редирект (`redirectGuestsTo` возвращает `null`). Тогда исключение аутентификации доходит до JSON-рендера и клиент получает 401.

## Подозрительно, но проблемой не является

- `orderByRaw('starts_at DESC')` в `index` похож на сырой SQL, но фрагмент константный, из запроса в него ничего не подставляется. Инъекции нет. Достаточно `orderBy('starts_at', 'desc')`. Фильтр `where('user_id', $request->user()->id)` корректный: чужие брони не отдаются.
- `capacity` комнаты нигде не проверяется. В правилах бронирования лимита по вместимости нет.
- Токены `anna-token` и `boris-token` постоянные. В README сказано, что это только демонстрация.

## Что не менялось по условию

`index` и `today` оставлены без исправлений. Правила бронирования исправлены в `store` и `destroy`. Редирект гостя с API тоже изменён: иначе запрос без `Accept` продолжал бы отвечать 500.
